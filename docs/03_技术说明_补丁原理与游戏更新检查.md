# 技术说明：补丁原理与游戏更新检查

## 1. 涉及的游戏文件

| 文件 | 内容 | 被哪些功能修改 |
|---|---|---|
| `GameAssembly.dll` | IL2CPP 编译后的游戏代码（x64） | 门派特性随特殊建筑、自创武学每品级9门 |
| `LongYinLiZhiZhuan_Data\il2cpp_data\Metadata\global-metadata.dat` | 类名 / 方法名 / 参数名（v27） | 只读，用于按名字定位方法 |
| `LongYinLiZhiZhuan_Data\resources.assets` | 数据表（TextAsset，CSV） | 合欢殿（BuildingData）、合欢宗主天赋（HeroTagData） |
| `LongYinLiZhiZhuan_Data\globalgamemanagers` | ResourceManager 资源路径表 | 合欢殿（地图造型、内景） |
| `LongYinLiZhiZhuan_Data\sharedassets0.assets` | UIAtlas 图集 | 合欢殿（建造列表图标） |

修改器全部用自己写的二进制读写（`Core.cs`），**不依赖 UnityPy 等第三方库**；只替换目标对象，其余字节保持原样。

### Unity SerializedFile（版本 22）要点
- 文件头大端：metadataSize@20 (u32)、fileSize@24 (i64)、dataOffset@32 (i64)。
- 对象表：pathID i64、byteStart i64（相对 dataOffset）、size u32、typeIndex i32。对象 8 字节对齐、紧密排列，无 TypeTree。
- 替换对象时按 (起点, 大小, 表序号) 稳定排序，重排后面的对象并更新文件头大小。（曾因排序不稳定导致输出不一致，已修复；`--idtest` 可验证原样替换后字节完全相同。）
- TextAsset 原始数据 = 对齐字符串 m_Name + 对齐字符串 m_Script（表内容是 UTF-8 CSV，带 BOM，行尾 `\r\n`）。
- ResourceManager（classID 147）：m_Container = 按字节排序的 (路径字符串, PPtr(fileID i32, pathID i64)) 列表，后接 m_DependentAssets。
- SpriteAtlas：name、m_PackedSprites（PPtr 列表）、m_PackedSpriteNamesToIndex（字符串列表）、其余。

### IL2CPP 定位方法
- global-metadata.dat v27：字符串表@24、方法表@48/52（每条 32 字节：nameIndex@0、paramStart@12、token@20、paramCount@30）、参数表@88、字段表@96、类型表@160/164（每条 88 字节：nameIndex@0、fieldStart@32、methodStart@36、method_count@64、field_count@68）。
- GameAssembly.dll 里搜索字符串 `Assembly-CSharp.dll` 找到 CodeGenModule：+8 方法数，+16 方法指针表；方法地址 = 指针表[token 的 RID - 1]。
- 修改器按「类名 + 方法名 + 参数名」定位（例如 `HeroData.HaveForceFunction(forceID)`），所以游戏更新后地址变化也能自动找到；再用固定的指令特征确认结构没变，不符合就报「不兼容」而不会乱改。

## 2. 各功能的具体修改

### 2.1 门派特性随特殊建筑（GameAssembly.dll）

游戏用 `HeroData.HaveForceFunction(forceID)` 判断「这个角色能否使用 forceID 号门派的门派特性 / 功能」。BuildingData 里特殊建筑的门派功能按钮条件就是 `我&门派功能N`（N = 门派编号）。

原版逻辑（关键部分）：角色所属门派 `belongForceID`（HeroData+0x84）必须等于 forceID，再查一个静态列表。

修改后：
```
force = hero.GetForce(includeServant: false)
area  = force?.MainArea()
return area?.FindBuilding(53 + forceID) != null
```
即「自己门派的主驻地里有 forceID 号门派的特殊建筑」就返回 true。特殊建筑编号 = 53 + 门派编号（53 销金窟 … 72 玄冰池，只有 0~19 号门派有）。53 这个基数是从 BuildingData 里含 `门派功能0-` 的那一行算出来的，不是写死的。

改法：把 `cmp [rbx+X],edi ; jne` 到函数尾声 `mov rbx,[rsp+30h]; add rsp,20h; pop rdi; ret` 之间的指令替换为 47 字节新代码（3 个 call + 判断），其余填 nop。检测标记：函数内出现 `48 8B CB 32 D2 E8`（mov rcx,rbx; xor dl,dl; call）。

其他门派完全不受影响：它们的驻地不会有别派的特殊建筑，而自己的特殊建筑本来就在。

**生效范围（代码确认）**
- 原函数开头的前置判断保留：只对 heroID == 0（主角，HeroData+0x58）返回 true，所以只有主角拥有这些特性，门派弟子没有。
- HaveForceFunction 在游戏里有约 90 处调用，既包括特殊建筑里的门派功能按钮（BuildingData 条件 `我&门派功能N`），也包括门派特性的规则效果，例如：痛饮（DrinkUIController.ManageDrinkBuff）、豪赌、行医 / 妙药（看病、疗伤、医治 NPC）、行乞（AskGiftFromNPC）、天工 / 巧匠（CraftUIController、EnhanceUIController）、禅宗 / 道法（GetMeditationTopic）、马术（ManageHeroHorseMove）、博引（GetIdentifyKnowledge）、杀手（CatchBadFamePlayerEventHappen、StartBeatRandomEnemy）、归宗（GameController.UpgradeSkill）、辩论（DebateUIController）、技艺经验（ChangeLivingSkillExp）等。
- 不受影响的：门派介绍里显示的特性文字（仍是自己门派的）、ForceSpeAddData 这类门派数值加成（来自门派自身数据，存档里是读档时重算的派生数据）。

### 2.2 自创武学每品级 9 门（GameAssembly.dll）

`WorldData.HavePlayerCustomSkill(rareLv)`：遍历 `WorldData.customSkills`（字典，值是 CustomSkillData：skillData@0x10、createHeroName@0x18、createByPlayer@0x20），原版只要找到一个「玩家创建 且 品级 == rareLv」的就返回 true → 每品级只能 1 门。
调用者：`PlotController.StartCustomSkillEntry`（选项旁显示已创建）和 `PlotController.CustomSkillChooseLevel`（选了已创建的品级会被拒绝）。

修改：在匹配处改为计数（用 dil 寄存器，函数开头已清零）：
```
cmp [rcx+34h],ebx ; jne 下一个   ; 品级相同才算
inc dil
cmp dil,9         ; 不足 9 个继续遍历
jb  下一个
```
遍历自然结束时原函数返回 false（状态 0x63），只有中途 break（0x65）才返回 dil，所以不足 9 个返回 false，满 9 个返回 true。共改 16 字节。上限常量 `GamePatcher.MaxCustomSkills = 9`。

### 2.3 秘籍持有数量提示（GameAssembly.dll，新增代码节）

`QuickDetail.ShowBookQuickDetail(target, bookData)` 生成秘籍的悬停提示（第二个参数实际是 ItemData），右侧的特效框（无敌、慧眼、杀机…）由 `QuickDetail.AddDescribeTab(text)` 逐个添加。

修改：
- 在 DLL 末尾新增可执行节 `.hhbook`（PE 头加一个节表项，SizeOfImage 增大；代码只用相对跳转，不需要重定位）。
- 把函数尾声第一条指令 `movaps xmm6,[rsp+40h]`（5 字节）换成 `jmp .hhbook`，新代码执行完再执行这条指令并跳回。
- 新代码（源码 `tools\bookcnt\cave.asm`）：取悬停秘籍的 skillID → `WorldData.Player()` 得到主角 → 遍历 `itemListData.allItem`（背包）和 `selfStorage.allItem`（个人仓库）；再用 `HeroData.GetForce(false)` 取主角所属门派，遍历 `forceStorage.allItem`（宗门仓库）和 `bookStorage.allItem`（藏经阁）。统计 type == 3（秘籍）且 skillID 相同的物品，按 rareLv（0~5 = 白绿蓝紫黄红）计数 → 用 `il2cpp_string_new`、`GlobalData.GenerateRareLvColorText`（按品质上色）、`String.Concat` 拼出文字：「背包：…」一行总是有（没有写「无」），仓库 / 宗门仓库 / 藏经阁三行数量为 0 时省略 → `AddDescribeTab` 加一个框。
- 用到的字段偏移（1.1.3）：HeroData.itemListData +0x220、selfStorage +0x228；ItemListData.allItem +0x28；ItemData.type +0x14、rareLv +0x40、bookData +0x70；BookData.skillID +0x10；ForceData.forceStorage +0xA0、bookStorage +0xB8。安装前逐一用游戏代码里的对应指令核对，不符就报不兼容。
- 改汇编后：`nasm -f bin -o cave.bin cave.asm`，再 `python gen.py <源码>\src\BookCountCave.cs` 生成机器码模板（gen.py 会找出 8 个外部目标的 12 处相对地址，安装时按实际地址填入）。
- 注意：新代码没有登记异常展开信息（.pdata）。所调用的游戏函数在正常情况下不会抛异常；万一出现异常，可能导致游戏崩溃，卸载此项即可恢复。

### 2.4 首次研读也可跳过（GameAssembly.dll，新增代码节）

原版 `ReadBookController.RealStartReadBook()`：首次研读先学会武学，然后 `HeroData.GetSkillMaxPracticeExp(skillID)` 取这门武学的研读记录（SkillMaxPracticeExpData，`maxReadExp` 是 6 个品级的最高研读经验）。记录为空、或本品级记录 ≤ 0 → 直接进研读面板；否则弹「是否跳过」，确认则 `AutoReadBook()` 得到 记录 × `GlobalData` 静态字段 +0x168（= 0.9）。研读完成时 `SureFinishRead()` 用更高的经验更新记录（没有记录对象就新建并 `AddSkillMaxPracticeExp`）。

修改：
- DLL 末尾新增可执行节 `.hhread`；把上面两处「进面板」的条件跳转（`je` / `jae`，各 6 字节）改为跳到新代码，条件不变。
- 新代码（源码 `tools\readskip\cave.asm`）：取这门武学的武学等级（`KungfuSkillLvData.DataBase()` 返回的 KungFuData，等级在 +0x34）；遍历人物的 `skillMaxPracticeExpData`，对每条记录用栈上的假 KungfuSkillLvData（只填 +0x10 skillID）调 `DataBase()` 查等级，只看同等级的记录：M = 它们在本秘籍品级上的最高值（没有就取它们所有品级的最高）。实得 = M × 0.8；同等级没有记录时实得 = 默认值（cave.asm 末尾 `defaults`，等级 0~5 = 400/900/1500/2100/2600/3100）。人物一条记录都没有（拿不到记录对象的类）→ 照旧进面板。记录 = 实得 / 0.9：记录对象为空时用已有记录的类 `il2cpp_object_new` + 构造函数新建，`AddSkillMaxPracticeExp` 加到人物身上，再用 `il2cpp_gc_wbarrier_set_field` 写入 ReadBookController；然后跳回原版「是否跳过」分支。跳过实得 = M × 80%。拒绝跳过则照常研读，读出更高经验时记录照常更新。
- 用到的偏移（1.1.3）：ReadBookController 人物 +0xA8、记录 +0xB0、武学 +0xB8、秘籍 +0xC0；ItemData.rareLv +0x40；HeroData.skillMaxPracticeExpData +0x250；SkillMaxPracticeExpData.skillID +0x10、maxReadExp +0x18；KungfuSkillLvData.skillID +0x10；KungFuData 等级 +0x34。安装前逐一核对，另外核对跳过比例仍是 0.9、`DataBase()` 仍只用 skillID 调 `GameDataController.GetSkillDataBase`。
- 改汇编后：`nasm -f bin -o cave.bin cave.asm`，`python gen.py <源码>\src\ReadSkipCave.cs`（7 处外部地址），`python test_emu.py cave.bin` 用模拟器跑几种记录组合。

### 2.5 拍卖自动出价（GameAssembly.dll，新增可读写代码节）

`AuctionController`（uGUI）：`startAuctionButton`(+0x28) 是开拍按钮，`playerAuctionUI`(+0x20) 下的 `OfferButton` 是出价按钮（点击 → `SureOfferMoneyButtonClicked`：`playerOfferMoney` ≤ 背包钱数时 `StartCoroutine(RefreshOfferMoney(钱, 主角))`）。`auctionStep`(+0x48) == 2 为竞价中；`nowOfferHero`(+0x98) 当前出价人；`offerRoundLeftTime`(+0x94)；`skipping`(+0xB4)；`havePlayer`(+0x4C)；`auctionItemList`(+0x58)[0] 是当前拍品；`GetNextOfferMoney()` = 当前价 + 最低加价。AI 出价走的也是 `RefreshOfferMoney` + `StartCoroutine`，协程第一步就同步设置出价人和价格。

修改：
- DLL 末尾新增节 `.hhauct`（特性 0xE0000020：代码 + 可读写，里面有三个变量：开关、待定开关、当前拍品）。
- `Button.Press()` 开头（`push rbx; sub rsp,20h` 6 字节）→ 新代码：取按钮名字，`hhAutoStart` → 记下「待定开关 = 开」后照常执行（复制来的按钮点击事件仍是开拍）；`hhAutoBid` → 切换开关并直接返回（不执行原来的手动出价）；其他按钮照常执行。
- `StartAuctionRoundButtonClicked()` 开头（同样 6 字节）→ 开关 = 待定开关，待定清零，记下当前拍品。普通开拍时开关就是关。
- `Update()` 里 `cmp [rbx+48h],0; mov [rsp+50h],0`（12 字节）→ 新代码，执行完再补这两条：
  - 开拍按钮下没有 `hhAutoStart` 子物体就 `Object.Instantiate(按钮, 按钮, false)` 复制一个，改名，`localPosition = (原按钮 sizeDelta.x + 8, 0, 0)`，把自己或第一层子物体上的 Text 设为「自动出价」；出价按钮同样复制出 `hhAutoBid`。复制出来的是原按钮的子物体，跟着原按钮显示 / 隐藏。
  - 每帧把 `hhAutoBid` 的文字设为「自动出价 / 停止自动」，并设为可点。
  - 开关开 + 竞价中 + 主角参拍 + 没点跳过 + 剩余时间 > 0 + 当前拍品是开拍时记下的那件 + 当前出价人不是主角：下一口价 ≤ 背包钱数 → `StartCoroutine(RefreshOfferMoney(下一口价, 主角))`；否则关开关。
- 取组件用 Update 里游戏自己的 `GetComponent<Text>` / `GetComponent<Button>`（共享泛型代码 + MethodInfo 槽，Update 开头已初始化）；取主角用 Update 里同样的静态 getter + `WorldData.Player()`。
- 安装前核对：三处钩子的原始字节、上面所有字段偏移、Update 里的字符串常量 `OfferButton`（从 metadata usage 编码解出字符串常量下标再查 global-metadata）。
- 改汇编后：`nasm -f bin -o cave.bin cave.asm`，`python gen.py <源码>\src\AutoBidCave.cs`，`python test_emu.py cave.bin`（用模拟的 Unity 对象跑 21 种情况：建按钮、按钮位置和文字、点按钮、各种不出价条件、钱不够停止、寄存器和栈恢复）。
- 游戏里还没实测；如果按钮位置挡住别的按钮，改 `k_gap` 或位置计算即可。

## 3. 安装 / 卸载 / 备份逻辑（Patches.cs → GamePatcher.Analyze / Apply）

1. 对每个文件，用各功能的检测函数判断当前文件是否被改过：
   - 没改过 → 当前文件就是原版。
   - 改过 → 读 `.bak` 作为原版（`.bak` 也被改过则报错，需 Steam 验证完整性）。
2. 每个功能单独在原版上试装一次，失败 = 不兼容（显示原因，不能勾选）。
3. 已安装功能集合重新生成一遍，与当前文件比较，不同 = 「已安装，可更新」。
4. 应用时：目标文件 = 原版依次叠加勾选的功能（DLL：门派特性 → 自创武学 → 秘籍持有数量提示 → 首次研读跳过 → 拍卖自动出价；resources：合欢殿 → 天赋）。与当前相同则跳过；第一次改某文件前把原版写成 `.bak`；写临时文件、校验 MD5 后替换。
5. 生成结果是确定的：同样的原版 + 同样的勾选 = 逐字节相同的文件。

## 4. 游戏更新后的检查清单

1. 关游戏 → 修改器「检测」。Steam 更新会用新原版覆盖补丁，状态通常变回「未安装」，旧 `.bak` 会在安装时被新原版替换。
2. 全部能勾选（没有红色「不兼容」）→ 直接「按勾选安装 / 更新」。
3. 安装后可以额外核对：
   - 合欢殿编号、合欢宗主天赋编号是否仍是 76 / 393（界面顶部、日志里会显示）。**如果游戏新增了建筑或天赋，编号会变，存档里引用的旧编号就对不上了**，需要另行处理存档。
   - `--status` 命令行输出。
4. 出现「不兼容」时的含义：
   - 「代码中找不到方法 …」：游戏改了类名/方法名/参数名 → 需要用 `tools\` 重新分析。
   - 「HaveForceFunction / HavePlayerCustomSkill 结构与预期不同」：函数内容变了 → 用 `tools\ndis.py` 反汇编比对后更新特征码。
   - 「建筑表 / 天赋表 / 效果表里找不到 …」：数据表改了列名或删了「金顶」等。
5. 2026-11 更新的核对结果：所有方法签名不变，HaveForceFunction 只有一个与补丁无关的静态字段偏移变化（0x3a8→0x3b0），四项功能全部兼容；建筑 76 / 天赋 393 编号不变；新增内容是私宅练功房的「自创武学」。

## 5. 编译

`source\合欢宗修改器\build.bat`：用 Windows 自带的 .NET Framework 编译器
`C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe`（C# 5 语法，已确认可编译），输出 `合欢宗修改器.exe`。

在 Linux / mono 下：
```
mcs -nostdlib -noconfig -target:winexe -out:LongYinMod.exe \
  -r:/usr/lib/mono/4.5-api/{mscorlib,System,System.Core,System.Windows.Forms,System.Drawing}.dll \
  -codepage:utf8 -optimize+ src/*.cs
```
**必须引用 4.5-api 参考程序集**：直接用 mono 自带的 mscorlib 编译，会绑定到 Windows .NET 4.x 没有的 `String.Split(char, StringSplitOptions)` 重载，在 Windows 上运行时报「找不到方法」。

源码文件：
| 文件 | 内容 |
